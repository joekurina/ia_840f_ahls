## Specification mapping and limits

1. **Exact source, parentage and EOF.** `delivery.py:56–88` produces inert shell text; only `proposed_command` pins the real transport length/hash. The generic `command` intentionally accepts synthetic arbitrary bytes and is not a production binding gate. Short octal arguments feed a builtin printf pipe. The brace group does not replace or wrap existing bash in another shell; `/usr/bin/python3 -I -B -S -` is its pipeline child (`:61–72`). Writer closure supplies EOF. Extra adapter descriptors are closed in the diagnostic child. The successful synthetic parentage/EOF evidence supports this design, not current target attestation.
2. **Separate original streams and genuine status.** Encoders separately read stdout/stderr and use one blocking write per bounded record into the same pipe; the relay is the sole framed-data writer to the PTY (`:14–34,66–79`). The generator uses 288-byte chunks and a 512-byte record limit. Bash captures PIPESTATUS immediately; S carries Python's pipeline-element status, not tmux's exit code, plus helper/writer statuses. Both stream EOFs and successful relay/restoration R are mandatory (`:145–161`). Nonzero Python status is preserved.
3. **Capture bounds.** Each decoded stream allows 3 MiB inclusive; raw capture allows 32 MiB inclusive (`:8–9,107,150`). The parser accepts canonical base64 frames up to 384 decoded bytes, wider than the generator's 288, but still bounded (`:148`). The generic generator has no payload-size cap; the production proposal's binding fixes the actual payload. The fixture continuously captures before load/paste, with a 90-second reader deadline and 75-second completion wait (`fixture.py:32–59,77–91`). A read may retain up to one 64 KiB overshoot before rejection. Evidence covers substantial framing/escaping expansion, not unlimited fragmentation; cap excess is incomplete, not truncation accepted as success.
4. **Failure classification.** `delivery.py:105–160` rejects missing status/restoration, incomplete channel endings, sequence/base64 faults, unsupported/malformed control records, unmatched acknowledgements, disconnect/lag/error indicators, and limits. Prompt/command echo is deliberately not channel data. A caller must provide a finished, correctly bounded acquisition and external-channel errors; the pure parser cannot infer an unreported disconnect outside supplied bytes. Local polling re-parses retained data; it does not retry execution (`fixture.py:79–91`). There is no remote controller or automatic remote retry.
5. **Receiver contract.** README `:135–140` specifies exact stdout envelope bytes, separate outer stderr and S's Python integer status, with every capture/decode/limit/timeout error conveyed as transport error. This matches receiver `receiver.py:86–100`: command status, not collector wait status or tmux status; errors remain incomplete. No receiver invocation is implemented. `delivery.py:161–162`, manifest and retained final fixture records preserve `authorization`, `ready_for_build`, and `vendor_run` false.
6. **Resource boundary.** Proposed shell text uses pipes/process substitutions/coproc and descriptor redirections, not remote regular files or a new remote pane/session/socket. This still requires explicit permission under unchanged sibling redirect restrictions. New-session/kill-server operations belong only to the private local fixture (`fixture.py:22–25,46,114–137`) and cannot be transplanted to the target.

## Concrete production blockers, not waived by disclosure

- **Asynchronous setup is not a launch gate:** `delivery.py:64–71` checks SAVE's status, but does not establish relay/encoder readiness before the diagnostic pipeline. A helper can fail after process-substitution/coprocess setup while the diagnostic still starts, then hangs or loses output. S/R validation prevents accepting that acquisition, but does not prevent the attempted diagnostic. Smallest production correction is a reviewed helper-readiness/descriptor gate before dispatch if fail-before-start behavior is required; alternatively a fresh decision must explicitly accept this attempted-execution failure mode. README `:189–191` alone grants neither safety nor permission.
- **Restoration is normal-path, not guaranteed recovery:** SAVE changes terminal state before helper setup (`delivery.py:35–45,64`); RESTORE runs only after pipeline/helper waits (`:73–81`). Abrupt bash death/SIGKILL, interruption, a stuck helper, or setup failure can leave modified terminal attributes or resources. Successful R and retained termios comparisons support ordinary/nonzero-exit restoration only. Smallest production prerequisite is an explicit failure/terminal-recovery policy that does not invent retries or silently replace shell traps; no same-process trap can guarantee recovery after SIGKILL.
- **No production acquisition/controller boundary:** the fixture deliberately terminates its own client after completion and retains shutdown bytes (`fixture.py:111–123`). Remote identity, exclusive pane ownership, shell options/hooks, free descriptors/variables, helper runtime compatibility, channel error propagation, and receiver integration remain unimplemented/unverified (README `:153–197`). A reviewed real controller must bind these and preserve a defensible acquisition-versus-shutdown boundary before any execution decision.
- **Cleanup evidence is local and limited:** final cleanup calls kill-server and checks only its owned socket; the code treats any nonzero list-sessions result as server absence (`fixture.py:124–134`). That is not a general proof of absence under arbitrary query failures. Retained fixture 08 specifically records kill-server success and an explicit “no server running” response (`commands.json:106–126`), and all eight private socket paths are currently absent. `owned-cleanup.json` records the same explicit no-server response for earlier stale sockets. No live process query was performed in this review. Do not reuse this inference as remote cleanup authority.

These limitations do **not** defeat a package whose deliverable is local stdlib preparation, inert proposal text, and retained synthetic demonstrations. They **do** prohibit upgrading this scoped PASS into actual remote-execution safety or authorization. Quality review remains separate; fresh permission and identity review are required before any production attempt.
