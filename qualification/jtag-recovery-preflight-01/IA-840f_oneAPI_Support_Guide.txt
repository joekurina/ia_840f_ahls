1 Overview
Intel oneAPI/oneASP supports oneAPI ASP FPGA packages as targets. This technical note is intended to
help clarify the steps required in getting started with the BittWare oneAPI ASP packages within
oneAPI/oneASP, specifically in relation to the IA-840f. These steps have been tested against Intel oneAPI
2024.1.0 specifically, but Intel’s support model is to provide only the latest version of oneAPI in their down-
load site. Therefore, when you access, you may not see 2024.1.0 as an available version. Intel oneAPI
2024.1.0 toolkit installer does not support the FPGA add-on (Quartus) selection; Quartus must be installed
separately; thus, the intelfpgadpcpp folder is not inside the oneAPI root directory. For further details on
FPGA add-on (Quartus) installation, refer to the link below: https://www.in-
tel.com/content/www/us/en/developer/tools/oneapi/fpga.html Unlike previous generations of BittWare
oneAPI ASP deliverables, such as on BittWare 520N-MX product, the IA-840f oneAPI ASP deliverables
are based on Intel OFS approach. Intel OFS is considered BETA.
This code release is supplied under MIT license terms as per the current OFS release model as of OFS
2023.1. The DFL driver and OPAE SDK installation steps are now closer to the original IA-840F release:
there is no longer the need to build a kernel or the OPAE SDK from source.

This technical note will provide guidance to:

    l   IA-840f standard RPM installation and requirements for ASP packages
    l   Install Intel oneAPI
    l   Install BittWare IA-840f oneAPI ASP package
    l   Verify ASP and card installation
    l   Build and run a basic vector-add example

2 Included ASP Variants
The file set contains two variants of ASP variants. One of which is denoted ‘_usm’ and is provided to allow
for preliminary support for USM/SVM within oneAPI and OpenCL approaches. Please refer to the known
issues section for further comments regarding USM based ASP. In the current release, both ASPs, are
based on an OFS minimized approach to restrict the total number of features implemented to maximize the
available FPGA user resource. This means that not all features on the IA-840F are exposed in the current
ASP variants. In comparison to earlier generation BittWare BSP deliverables, the current IA-840F ASP
packages, do not include or support the feature of external channels via QSFP type ports or modules. It is
intended to expand the feature set of these ASPs in the future once external channels are fully supported in
oneAPI itself. The following details the ASP variants included in this initial release.

ofs_ia840f

   l   Based on AGFB027R25A2E2V device
   l   Two DDR4-2666 banks available to kernel targeting on on-board DDR4 bank (32GByte total)

ofs_ia840f_usm

   l   Based on AGFB027R25A2E2V device
   l   Two DDR4-2666 banks available to kernel targeting on on-board DDR4 bank (32GByte total)
   l   USM/SVM host based shared memory access option

In both cases these ASP variants are based on a minimized OFS FIM design to maximize the available
user FPGA logic. The following floorplan overview highlights the approach taken. The static portion of the
design is currently minimized to an area in bottom left corner of the device. As oneAPI develops further,
other ASP variants may be offered or developed that extend the features exposed on the IA-840F. These
will require changes to the illustrated floor plan and therefore the consumed FPGA logic resources, depend-
ent upon the new ASP variant(s).

3.1 Operating Systems Verified with oneAPI ASP Package

Note that we have tested primarily on RedHat 8.9 series systems since this is the preferred oneAPI oper-

3.1.1 System Requirements and Boot Options:
Intel OFS and OPAE require specific settings in the host system BIOS and the Linux grub command boot
arguments. BIOS settings required as follows:

  1. SR-IOV / SR-IOV global enable : ENABLED
  2. VT-d & virtualization extensions : ENABLED
  3. Secure Boot : DISABLED

3.1.2 Grub boot options:

  1. It is a requirement to enable iommu and hugepages via grub command line options as follows: sudo
     emacs /etc/default/grub and add following parameters, "intel_iommu=on pcie-
     e=realloc hugepagesz=2M hugepages=2048" within the GRUB_CMDLINE_LINUX para-
     meter. Here's an example of how it should look: GRUB_CMDLINE_LINUX="<default_prams>
     intel_iommu=on pcie=realloc hugepagesz=2M hugepages=2048"

3.7 OneAPI-ASP

3.7.1 Overview
This directory contains files necessary to generate ASP for the OFS IA840F reference platform. The
hardware currently relies on platforms that implement the OFS PCIe TLP format using AXI-S interfaces,
and the software uses OPAE SDK interfaces.

3.7.2 Directory Structure
The Directory is structured as follows:
   l   bringup: contains files used by 'aocl install' command to install prerequisite software on a target
       system and to load a ASP. The files are stored in two separate git submodules that each use git-lfs
       to store their contents.
   l   hardware: contains files used by the OneAPI compiler to integrate the generated kernel code with
       platform specific code. Contains distinct shim targets with distinct functionalities (ex. USM and
       non-USM variants targeting the same board platform).
   l   linux64: contains the libraries and utilities that are used by the OneAPI software stack. The repos-
       itory itself contains a few scripts that are checked-in to linux64/libexec. The linux64 directory is
       also the target for files compiled from the source directory.
   l   scripts: a variety of helper scripts used for configuring ASP and for running tests

3.7.3 ASP variants
The hardware folder contains subdirectories with the 2 different Shim/BSP variants:
   l   ofs_ia840f_usm: Shim/ASP that supports shared virtual memory between host and device.
       This variant is the same as the non-USM variant with the addition of the USM path between the
       kernel-system and the host.
   l   ofs_ia840f: DMA-based Shim/ASP that supports local memory and host memory interfaces for
       the kernel system.

4 Setting up the Hardware
4.1 Updating the oneAPI ASP FPGA Image

The IA-840f hardware is shipped with a factory test image. This is not an oneAPI ASP FPGA image;
instead it is a Card Test application image, so the card configuration will need to be updated for use with
oneAPI. Before following these programming steps, connect a USB-C cable to the IA-840f USB IN PORT
as shown in the BittWare IA-840f Hardware Reference Guide https://developer-
.bittware.com/hardware/docs/ia-840f/Rev1/Content/HardwareReference/BoardOverview/Board_Lay-
out.htm

4.2 Updating the FPGA Image (sof) Manually

The following instructions describe manually programming the FPGA directly using a SOF-based bit-
stream. This is not therefore a permanent change to how the card boots from a cold power-on, but it is
recommended as an initial step to get familiar with the hardware. The next section details the process to
change the flash boot load on the IA-840f if required.

  1. Before reprogramming the FPGA that is live on the PCIe bus, we strongly recommend disabling AER
      using the provided script. Otherwise, you may experience a watchdog-based system reboot due to a
      fatal PCIe error being detected.
          l   Change to the IA-840f ASP folder: cd /path/to/intel/oneapi-asp/ia840f
          l   Call the AER script for a number of possible live IA-840f combinations using the following:
              sudo ./control_aer.sh 12ba:0070 off; sudo ./control_aer.sh 8086:bcce
              off; sudo ./control_aer.sh 8086:bccf off; sudo ./control_aer.sh
              1af4:1000 off; sudo ./control_aer.sh 12ba: off




  © 2024 BittWare, a Molex company                                                                          17
          l   For enabling the JTAG access via Quartus please make sure to follow the steps mentioned
              in this link: https://www.intel.com/content/www/us/en/docs/programmable/683472/21-4/in-
              stalling-on-red-hat-enterprise-linux.html Failure to update the rules file may cause issues
              with the Quartus tools JTAG functionality.
  2. Program the required IA-840f oneAPI ASP SOF into the FPGA using Intel Quartus programmer.
      Program the FPGA using the required SOF from the command line: Change the directory to the
      Quartus binaries folder
          l   cd /path/to/quartus/intelFPGA_pro/23.1/quartus/bin/
          l   ./jtagconfig --setparam 1 JtagClockAutoAdjust 0;./jtagconfig --set-
              param 1 JtagClock 16M;./jtagconfig --getparam 1 JtagClock
          l   ./quartus_pgm -c 1 -m JTAG -o "p;/path/to/intel/oneapi-asp/i-
              a840f/build/bringup/ofs_ia840f/build/output_files/ofs_top.sof@1"
          l   Note: In this release, the path to the SOF is: ~/IOFS_BUILD_ROOT/ofs-ia840f/work-
              ofs-23.1-2-build/syn/syn_top/output_files/ofs_top.sof
  3. Restart the host system: shutdown -r now


4.3 Updating the Flash FPGA Image

Rather than loading the SOF-based bitstream after each cold boot, you can update the flash on the IA-
840f to directly boot as an oneAPI ready device on the IA-840f. This section details these steps to repro-
gram the user flash page in the QSPI flash that is connected to the Agilex series device on the BittWare
IA-840f. This is an optional step. For flash update to user page based on page setup from a factory pro-
grammed card:

  1. Change directory, cd, to the archive subfolder flash_image.
  2. Call the Bittware Agilex flash programmer utility (bw_agilex_flash_programmer, which is
      included in the BittWare SDK) to update the user page with the following command: bw_agilex_
      flash_programmer program -a 0x04000000 ia840f-ofs-23.1-2-flash-
      image.rpd

Once the flash page has been updated you should shut down the system to power cycle the card. On
next cold boot it will load the new image from flash and be ready for use as an oneAPI target device.

4.4 Initializing the oneAPI ASP Device

After updating the PCI-based FPGA image with either of the above steps, manual or flash-based load,
you’ll need to complete some final steps once back into the OS. This can be automated in a startup

7.1 HTML Reports

The compiler includes a flag for generating "early-image" reports:


   icpx ... -fsycl-link=early ...



Once the report is created, there should be a directory ending in '.prj' in the current working directory. This
directory contains generated RTL code for your design, FPGA resource estimates for your design, and an
optimization report. To view the optimization report in a browser window use the following command:


   fpga_report <name-of-example>.fpga.prj




7.2 vTune Profiler

The vTune profiler is included with the installation of oneAPI. The following metrics are collected during pro-
filing:

    l   Global Bandwidth
    l   Stalls
    l   Occupancy
    l   Activity
    l   Idle




  © 2024 BittWare, a Molex company                                                                           39
Profiling is enabled by using the following compilation flag:


   icpx ... -Xsprofile ...



To use the command line version of vTune, simply use:


   vtune -collect fpga-interaction /path/to/executable



This command will execute the profiled oneAPI binary and display various perfomance metrics and bot-
tlenecks. As the name suggests, 'fpga-interaction' is used for getting information on oneAPI designs tar-
getting FPGAs. Many of the other vTune features are not intended for FPGA designs.
To use the GUI version of vTune, run the following command:


   vtune-gui



The vTune GUI displays all the same information as the command line version but it gives a richer pic-
ture of what your oneAPI design is doing. The GUI allows users to actually see how the CPU and FPGA
work in conjunction to execute oneAPI binaries.

8 Known Issues
8.0.1 Multiple Card Verification
The supplied ASP file set has only been verified in the configuration of a single IA-840f per host currently.
There is not a known limitation in this regard, but initial testing in the best known configuration has been lim-
ited to a single IA-840f.

8.0.2 Memory allocation failure and ulimit configuration
To ensure proper memory allocation and ulimit configuration for OneAPI, specific adjustments are
required. The following modifications should be made to the ulimit settings: OneAPI requires the max
locked memory and max memory size to be modified as followes: ulimit -a Output:


   core file size               (blocks, -c) 0
   data seg size                (kbytes, -d) unlimited
   scheduling priority                  (-e) 0
   file size                    (blocks, -f) unlimited
   pending signals                      (-i) 254934
   max locked memory            (kbytes, -l) 67108864
   max memory size              (kbytes, -m) unlimited



These settings should be set after initializing the OFS based ASP: aocl initialize acl0 ofs_ia840f. It's import-
ant to log out and log back in or reboot the system to take the effect, however if these settings are not con-
figured properly, the aocl diagnose acl0 will fail due to memory allocation problems. In the event of memory
allocation problems or if the ulimit configuration fails again, there are additional steps to consider for limit
settings:

    l   Navigate to the /etc/systemd/ directory on your system.
    l   Using a text editor, open the user.conf and system.conf files.




  © 2024 BittWare, a Molex company                                                                            41
   l   Uncomment and set the DefaultLimitMEMLOCK to the required size, for example: DefaultLim-
       itMEMLOCK=67108864

Note that user.conf represents the soft limit and system.conf represents the hard limit.
